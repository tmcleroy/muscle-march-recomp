## Execution (Milestone 1)

- `build/out/wiiparty.exe extracted [seconds]` loads the DOL, prepares low memory and runs `entry`; if it stops making progress it prints the call stack
- With the real boot data (`engine/src/core/boot.cpp`, checked against Dolphin RAM dumps in `reference/ram-dumps/`), `OSInit` follows the true path, checks the disc drive (`0x8015bb60`) and finishes. The game reaches `main`, passes several video retraces, creates threads, reads data from the disc, initializes GX, VI, LYT, G3D, EF and RFL, loads and links `boot.rel`, runs its `_prolog`, reads `locale/en_EU/boot/strap.arc.lz` and enters the scene task loop (`0x80069ee0`), without blocking
- With incomplete boot data it reached `main` (`0x800070e0`) and waited for the vertical retrace in `VIWaitForRetrace` (`0x80147860`)
- Strategy: the SDK hardware is not simulated; functions are replaced by runtime handlers (`games/wiiparty/analysis/hle_functions.csv` lists the names, `games/wiiparty/analysis/symbols.csv` resolves them to addresses, `engine/src/core/hle.cpp` implements them)
- Replaced so far: `EXIInit/Lock/Unlock/Probe/GetID` (EXI bus without devices), `__OSInitAudioSystem` (DSP), `OSRealModeCall` (BAT), `IOSSendRequest` (all IPC with IOS, simulated in `engine/src/ios/ios.cpp`: devices `/dev/stm`, `/dev/fs`, `/dev/es`, `/dev/di` and NAND files)
- `sc` is a no-op (it only flushes caches in this SDK)
- `/dev/di` device (in `engine/src/ios/ios.cpp`): answers as a normal drive. Inquiry (0x12) returns zeros, unencrypted read (0x8d) outside the disc gives error 0x52100, ReportKey (0xa4) gives error 0x53100 and RequestError (0xe0) returns the last error; the other commands return success
- Interrupts: `WP_POLL` on every backward jump, every 16384 iterations, calls `poll_interrupts` (`engine/src/core/interrupts.cpp`); if the game has EE enabled and the retrace is due (fixed 20 ms period for now), it sets the flags at `0xCC002030/34` and calls the handler in the table at `0x80003040 + 4*24` with the current context in `r4`, then `OSSelectThread` (`0x8013fad0`)
- Threads (`engine/src/core/threads.cpp`): each game thread is a Windows fiber. Calls to `OSSaveContext` (`0x80138290`) are translated with `setjmp` (`wp_jump`) and `OSLoadContext` (`0x80138310`, replaced) returns to that point with `longjmp` or starts a new fiber if the context came from `OSInitContext`; registers are saved in the game's own `OSContext`. `OSSwitchFiber` (`0x80138400`) changes `r1` and calls the function. Windows only for now
- Controllers: `WPADInit` and `KPADInit` (`0x8017b5a0`, `0x80193cf0`) are replaced by empty versions (no controllers connected). Planned design: a neutral layer holding the state of one controller and pluggable backends (keyboard and mouse first; generic gamepads and real Wii Remotes later)
- `OSReport` (`0x80138880`) and `OSPanic` (`0x80138900`) are replaced and show the text formatted by the game (`engine/src/core/format.cpp`)
- REL (`recompiler/recomp_rel.py NAME...` or `--all`, output in `build/wiiparty/generated/modules/`): the game decompresses and links each module with its own `OSLink`. Each module is translated with synthetic addresses (`section << 24 | offset`); relocations are resolved at generation time: calls into the DOL are direct (`f_XXXXXXXX`), internal calls are direct (`f_<module>_<address>`), data addresses are `g_<module>_bases[section] + addend`, and addresses in other modules use `wp::external_address`. `engine/src/core/modules.cpp` identifies the loaded module by a signature (identifier, sections and bss size) and updates its bases at the first jump. The DOL targets requested by modules are stored in `build/rel_dol_targets.csv` and `recomp.py` adds them as entries
- `boot` module (identifier 1): 5 functions, 248 instructions; its 31 calls into the DOL, 18 own data addresses and 2 pointers in data resolve correctly
- Virtual NAND (`engine/src/ios/nand.cpp`, folder `games/wiiparty/nand`, ignored): default `SYSCONF` (English, 4:3) generated on mount, save and settings files with read, write and seek, and `/dev/fs` commands (create file and folder, delete, rename, attributes, list)
- Initial video state (`engine/src/core/boot.cpp`): control register `0xCC002002 = 0x0101` (PAL, active) and interrupt registers `0xCC002030/34 = 0x1001`. If the display is not active `VIInit` programs NTSC and the game picks `/locale/en_US`
- Debugging: `WP_LOG_DISC=1` shows disc reads, `WP_DUMP=file` dumps memory on failure
- Pending: derive the retrace rate from the video mode the game configures, free the fibers of finished threads, and real disc data reads, OS threads, time, real DVD, NAND file reads (SYSCONF, `play_rec.dat`)

## Hypotheses and known problems

- Lifter: the OE (overflow) bit is ignored; `fres`/`frsqrte` use `1/x` instead of the Broadway estimate table; `blrl` and indirect calls depend on `g_function_table`
- Lifter: 172 `bctr` without a detected jump table; 158 are virtual calls (`lwz`+`mtctr`+`bctr`), treated as an indirect jump and return; 14 remain to be reviewed
- Lifter: besides `dol_functions.csv`, it discovers entries from `bl` targets, external jumps, pointers in data, `lis`+`addi` address constants and table targets; a function that falls into the next one is linked with a final call
- Lifter: function bounds = next entry of `dol_functions.csv`; no runtime yet (uninitialized memory, hardware, `sc`, exceptions)

- Ghidra 12.1.3 does not ship the Gekko/Broadway processor; the one from the GameCube Loader is used (installed in `%APPDATA%\ghidra\ghidra_12.1.3_PUBLIC\Extensions\`, source in `ghidra/extensions/`)
- Names of very small functions in the Dolphin map can be wrong (for example `OSGetCurrentContext` on several different getters), because the signature database gives the same name to identical bodies
- Ghidra has no EABI ABI; the `default` (System V PPC 32) is used
- The header BSS overlaps `.data5`-`.data7`; `LoadDol.java` only creates BSS blocks in the gaps

- The game logic lives mostly in the RELs: the recompiler has to support dynamic loading and REL relocations, not only the DOL
- The DOL holds the SDK and the common engine; the RELs are loaded per scene

## State after translating all modules

- The 115 REL modules are translated (`python recompiler/recomp_rel.py --all`, about 650 MB of C++) and the full executable compiles (about 316 MB). Recompiling everything takes on the order of 15 minutes with 12 threads.
- Diagnostic profiler: `WP_PROFILE=1` samples the innermost function every millisecond and prints it when the timer expires; with `WP_DUMP=file` it also dumps the guest memory.
- The game's task engine (0x80069af0-0x8006a96c) uses `setjmp` (0x801c8a1c) and `longjmp` (0x801c8b20) as coroutines. The lifter emits a native `setjmp` at calls to `setjmp` and the runtime replaces `longjmp` with a fiber switch; a buffer whose link or stack differs from the saved one is treated as a new context and starts a fiber at the saved address. Modules must be regenerated to include this change.
- The locked cache (0xE0000000-0xE0003FFF) has its own region in the memory buffer. It used to overlap low memory and `LCEnable` erased the system globals, including the interrupt table.
- `GXDrawDone` (0x8014fe50) is replaced: with no GPU, it finishes immediately by setting the flag it was waiting for.
- The retrace period is derived from the video configuration register (0xCC002002): PAL 20 ms, otherwise 16.683 ms.
- Current state: the game runs frames stably at about 50 per second, with the main thread and the frame thread, and loads the boot data. Without graphics output it is not yet possible to tell which screen it is on; the list of loaded modules is empty at that point.
- Audit of `main.dol`: the 14 illegal words are data inside the code area (the string "Metrowerks" and constant tables next to 0x80006680), the 169 indirect jumps without a table are jumps through a function pointer or virtual table and are resolved at run time with `wp::call`, and the 37 `rfi` are in the exception vectors and in functions already replaced or reachable only by real exceptions. No reachable code is left to translate in `main.dol`.
- Video output: `engine/src/platform/video.cpp` opens a Win32 window and, on each retrace, converts the external framebuffer (YCbCr 4:2:2, address and width taken from the VI registers) to RGB. The framebuffer stays empty because the GPU is not emulated yet; the game writes to the GX FIFO (0xCC008000) with ordinary instructions, so the next step is to capture those writes.
- Decoder fix: in D-form instructions (`ori`, `xori`, `addi`...) the last bit belongs to the immediate and is not the record bit. It was read as the record bit and overwrote cr0. Now only opcodes 4, 20, 21, 23, 30, 31, 59 and 63 accept the record bit. Checked with a decoder test and with a test of function 0x80039510 (red-black tree node erase) against libstdc++ `_Rb_tree_insert_and_rebalance` in `tests/wiiparty/lifted_tests.cpp`.
- GX FIFO capture: writes to 0xCC008000 (including those from `psq_st`) accumulate in `engine/src/gpu/gx.cpp` and are decoded command by command (CP, XF, BP registers, display lists and draws); with `WP_LOG_GX=1` a summary is printed for each EFB copy to the framebuffer.
- Per-thread diagnostics: each fiber has its own call trace; the timer prints the stack of all fibers, and `WP_WATCH=address` reports changes of one memory word.
- The GX FIFO decoder now interprets the game's stream with no errors (0 unknown commands). Both floats of a `psq_st` pair go to the FIFO. `WP_LOG_GX=2` lists the draws (vertices, VCD and VAT) and `3` the first commands. Each frame in the current state contains three quads and one EFB copy to the framebuffer.
- GX renderer on Direct3D 11 (`engine/src/gpu/gx_render.cpp`, state and vertices in `engine/src/gpu/gx.cpp`): vertex decoding by VCD/VAT with direct or indexed attributes, transformation by the XF matrices (projection, viewport, texture coordinate generation), ubershader with the TEV stages, texture decoding (I4, I8, IA4, IA8, RGB565, RGB5A3, RGBA8, CMPR), blending, depth, scissor and EFB copy to the external framebuffer converting to YCbCr 4:2:2. The first game screen (the strap notice) is drawn correctly. `WP_SAVE_FRAME=file.png` saves the presented image every 100 frames.
- Verified details: the game's cull mode 1 is equivalent to discarding faces with counter-clockwise winding on screen; the four masked BP registers (0xFE) apply to the next register; the TEV KONST constants share addresses 0xE0-0xE7 with the color registers and are told apart by bit 23.

## Display lists and closing the intermittent failure (2026-09-21)

- Cause: `GXBeginDisplayList` redirects the write pipe (0xCC008000) to a memory buffer by changing the PI registers (base 0xCC00300C, write pointer 0xCC003014) while the CP registers (0xCC000020/22) still point to the main FIFO. The runtime sent those bytes to the GP instead of to memory, so the commands executed at the time they were recorded and the saved list held garbage. When it was called later (command 0x40) the parser read absurd addresses and lengths: intermittent segfault (4 of 6 runs) and missing text.
- Fix (`record_display_list` in `engine/src/gpu/gx.cpp`): if the PI base differs from the CP base, the bytes are written to memory at the PI pointer and it advances. Also, a list call out of range is discarded with the warning `GX display list out of range`.
- Verified: 6 consecutive runs of 25 s with no failures (before, 4 of 6 with a segfault), ctest 3/3, and the main menu now shows the text (Suggestions, Rankings, Minigames, 1 to 4 players, About 45 min.).
- New diagnostic: `WP_LOG_FROM=N` with `WP_LOG_GX=2` starts the draw log after copy number N; texture maps and vertex arrays are shown.
- Still pending: black menu background (the 3D background draws come out with invalid vertices, cause not investigated; the badly recorded lists may have been the reason, to be rechecked) and partial House Party panel.

## Skeletal 3D models: diagnosis (2026-09-21)

- Dolphin reference provided by the user: the title has a pink/white background with 3D Miis and animals, the menu has a pink gradient background, red/orange/green panels and purple/blue/yellow buttons, and House Party shows 4 Miis. Our render: black background, no 3D models and different panel colors (blue/purple/green, turquoise/lime/purple buttons).
- Evidence: the model draws (commands 0x90/0x98/0xA0 with a position matrix per vertex) arrive with correct raw positions, but the XF matrices they use (indices 3, 6, 15, 27...) are zero. They are loaded with indexed loads (commands 0x20 and 0x30) from arrays of 48 bytes per matrix (different bases per model in MEM1), and the contents of those arrays are zero also when the FIFO is processed at the moment it is written (a flush threshold of 64 bytes was tried and reverted). So it is not a problem of delayed parsing.
- Ruled out: `PSMTXConcat` (0x8014b100) is compared with a reference matrix multiplication with 50 random cases and matches (test added in `tests/wiiparty/lifted_tests.cpp`); the constant `(0,1)` it uses is at 0x802f58d0.
- Pending: find which code should write those arrays (computation of the models' world matrices) and why it does not, or stores zeros; hypothesis: a function replaced by HLE, a thread/coroutine that never runs, or skeleton data not loaded.
- Not investigated yet: menu color difference and performance (the user perceives 30-40 fps with drops).

## Target platforms and the decision on aurora (2026-09-21)

- User's goal for final versions: Windows 10 and 11 (32 and 64 bits respectively, x86 and ARM), Linux and macOS.
- Current state, all Windows-specific: GDI window (`engine/src/platform/video.cpp`), Direct3D 11 with HLSL (`engine/src/gpu/gx_render.cpp`), threads as Windows fibers (`engine/src/core/threads.cpp`), build with GCC from MinGW-w64.
- Consequences: Linux and macOS need a cross-platform graphics backend (WebGPU with Dawn or similar), a portable window and input layer (SDL3) and portable coroutines. Windows 11 does not exist in 32 bits; a 32-bit executable with about 320 MB of guest memory and about 300 MB of code is the riskiest target and is left for the end.
- Decision: aurora (MIT) is not adopted whole for now. The Direct3D 11 renderer is kept to get a working game, and `engine/include/wp/gx_render.h` is kept as a narrow boundary (draw, copy, clear, load palette) so a WebGPU backend can be added later. Pieces of aurora without graphics dependencies (texture conversion) can be incorporated under its MIT license when they help.

## Locked cache DMA: cause of the missing 3D models (2026-09-21)

- Cause: the game moves matrices and other data with locked cache DMA (`LCLoadBlocks` at 0x80137c40 and `LCStoreBlocks` at 0x80137c70, writes to SPR registers 922/923 DMA_U and DMA_L). The runtime stored the write without doing the copy, so the skeleton matrix arrays stayed at zero. In Dolphin's RAM dump those arrays held real matrices (evidence that the game does compute them).
- Fix: `wp::locked_cache_dma` (`engine/src/core/runtime.cpp`) performs the copy when DMA_L has the trigger bit (memory to cache with the load bit, cache to memory without it; length in blocks of 32 bytes, 0 means 128) and clears the trigger and flush bits. The emitter (`recompiler/ppc/emit.py`) calls it after `mtspr 923`.
- Tool: `recompiler/recomp.py` no longer rewrites generated files that have not changed nor deletes existing ones, so a change to the emitter only recompiles the affected files.
- Verified: with the main menu the 3D background and the four House Party Miis are now visible (captures `d_04`, `d_05`). ctest 3/3.
- New visible problems: the image looks washed out (too light, with a white veil) and fps drop to about 5 in 3D scenes (50 fps on 2D screens). Not investigated.

## Decrementer and OS alarms; Mii database (2026-09-21)

- Cause of the RFL hang with the user's Mii database: after the read, the next stage is scheduled with an operating system alarm (`OSSetPeriodicAlarm`, about 19 ms) and the runtime did not emulate the decrementer (DEC) or its exceptions, so no alarm ever fired. A race condition was ruled out earlier (a minimum latency of 1 ms was added to asynchronous IPC completions, which is more realistic, but it was not the cause).
- Fix: `mtspr 22` and `mfspr 22` are emitted as `wp::set_decrementer` and `wp::get_decrementer` (`recompiler/ppc/emit.py`, `engine/src/core/runtime.cpp`), with the DEC tied to the time base clock. `poll_interrupts` delivers the decrementer exception (index 8 of the exception table at 0x80003000) with `save_context` and a resume point: the SDK handler saves the context, processes the alarms and ends with `OSLoadContext`, which resumes the interrupted thread or switches to another as on hardware. Leaving the interrupt through a fiber switch clears the interrupt flag.
- Diagnostics: `WP_LOG_IRQ=1` prints each decrementer exception; `WP_LOG_IOS=1` prints IOS requests and completions.
- Verified: with the user's Mii database (`RFL_DB.dat`, in a temporary unversioned NAND) the game finishes the RFL initialization (opens, seeks, reads and closes the file), shows the Miis from that database in the title, stays at 50 fps and reaches the Party Phil presentation with the correct pink colors of his clothes. With the default NAND it still reaches the menu. ctest 3/3.
- General effect: any game or SDK code that depends on alarms (DVD timers, `OSSleepTicks`, start buttons, RFL) now works; before it failed silently.

## Freeze when the first Mii moves on the board (2026-09-21, in progress)

- Reproduced with the scripted path plus periodic A presses (about 250 s in). The main fiber stays inside `0x80126ad0`, a rotation-matrix builder from three Euler angles that reduces each angle by repeated subtraction. It never finishes when an angle is huge.
- The caller is `0x8005ade0`, which reads the rotation of an object at `+0xb8`, `+0xbc` and `+0xc0` (vtable `0x80400f4c`) and calls `0x80126ad0`. The Y angle (`+0xbc`) follows `a' = -2a - k` each frame, so its magnitude doubles and alternates sign (for example -2150, 2150, -6451, 10752, -23654, 45158) until it reaches about 1e12. The X and Z angles converge normally (each step is about 0.95 times the previous one).
- This looks like a proportional controller with a gain of 3 per step on the Y angle, which diverges. The gain is probably scaled by a time step or another value that differs from real hardware. The source of that value has not been found.
- The rotation setters are `0x80053de0`, `0x80053df0` and `0x80053e40`. The next step is to log who calls them with a large Y angle. Object addresses change between runs, so a fixed memory watch does not work; log at the setters instead.
- Checked and ruled out: the semantics of `ps_sum0` and `ps_muls0` match the PowerPC manual and the Dolphin interpreter.
- Other findings from the same session, not yet investigated: the barrel in the first minigame does not appear, the dice have no pips, Miis look flat (GX lighting is not implemented, which fits), and round text such as "Round 1" is not drawn.

## Menu panel colors: solved, it is an intentional random shuffle (2026-09-22)

- Traced the array feeding `0x8000ffd0`/`0x8000fff0` (the color-id source for `f_menu_01012470`'s 8 on-screen items) at the two points that touch it: the fill loop and the read loop.
- The fill loop (`f_menu_010133c0`, a `std::vector`-style `push_back`) pushes exactly `0, 1, 2, 3, 4, 5, 6, 7` in that order, confirmed by logging the pushed value on each of the 8 calls (`PUSHBACK item_val=0..7`). No discovery, no hashing: this part is a trivial, always-identical fill.
- Between the fill and the read, the game calls `f_menu_01012960(begin, end, 0x8006b590)` on that array. Reading its body: it is a textbook in-place Fisher-Yates shuffle (loop from `count-1` down to `1`, at each step calling the third argument as `index = rng(i)` and swapping `array[i]` with `array[index]`).
- `0x8006b590` is a Park-Miller-style linear congruential generator with a global seed at `r13-0x8a38`. On its first call (seed == 0) it seeds itself with `OSGetTick() ^ 0xD8260000 ^ 0x0000BC89` (`0x80140b60` is `OSGetTick` per `build/wiiparty/symbols/dolphin_symbols.csv`); after that it updates the seed in place on every call.
- Conclusion: the game itself randomly shuffles which of the 8 palette colors (`0x801DE148`) lands on each menu item, seeded from the console's boot-time tick counter. This is not a bug in the table (`0x8000ffd0`/`fff0`, both proven correct earlier), not a bug in the fill loop (proven to always push `0..7`), and not something our own runs disagree on by accident: three consecutive runs producing three different permutations (`3,1,0,4,7,2,6,5` / `1,4,0,3,6,7,2,5` / `3,1,2,0,6,4,5,7`, all logged with `VECAT` before the shuffle result) is the *expected* behavior of a tick-seeded shuffle, since our `time_base()`-derived tick value at the moment of the first RNG call is not identical from run to run (nor would a real console's be, run to run).
- This reframes the original observation (title pink vs. blue, Party Games red vs. blue, Pair Games orange vs. purple, House Party green matching both) as most likely two independent draws from the same correctly-implemented random pool, not a translation bug. The open question is whether Dolphin's own boot path up to this RNG's first call is timing-deterministic enough that it always reproduces the same seed across its own reboots (plausible, since a cold Dolphin boot of the same disc is a much more controlled/repeatable sequence than reality) — if so, Dolphin would show a *stable* shuffle every time even though that stability is itself circumstantial, not evidence of a canonical/intended color.
- Suggested verification for the user (does not require our tooling): cold-boot the same Wii Party disc in Dolphin two or three times in a row and check whether the Party Games/Pair Games header colors change between boots. If they do, this closes the investigation entirely with no code change needed. If Dolphin is consistently the same across reboots, that is still not proof our colors are "wrong" — it would only mean Dolphin's specific timing up to the RNG's first call is more reproducible than a real console's, which is expected of an emulator.
- Diagnostic method (all temporary, not committed, build/ is gitignored): logged every call to `f_menu_010133c0` (vector push) and `f_menu_01013700` (vector element address, dereferenced) inside `build/rel_code/menu_000.cpp`, plus the existing `0x8000ffd0`/`fff0` trace in `build/recomp/dol_000.cpp` (see the "menu panel colors" entry above for the exact recipe). All instrumentation was reverted before this commit; `cmake --build build/out` and `ctest` were re-run clean afterwards.
- No colors were forced, no table entries were swapped, and no game code was changed. This closes the investigation unless the Dolphin reboot test above shows something unexpected.

## Flat Miis: normals, per-vertex texture matrices and dual texture transform (2026-09-22)

- Cause of the flat look: Wii Party shades Miis (and other models) with environment/ramp textures sampled through texture coordinates generated from the vertex normal, not with GX color-channel lighting. The texgen path in `engine/src/gpu/gx.cpp` had four gaps: the normal was read and discarded, `source == 1` (normal) fell through to a constant coordinate, per-vertex texture matrix indices were skipped, and the dual texture transform (XF `0x1009`, `0x1050+i`, post matrices at `0x500`) was not implemented.
- Data gathered with temporary logging in `generate_texture_coordinates` (reverted) on the scripted path to Board Game Island: the Mii environment material uses `info = 0x05086` (source normal, STQ, ABC1) with per-vertex texture matrices (`vmask` 01/03/06, indices 30-57) that hold each bone's normal rotation, dual transform on, and post matrix `[0.5 0 0 0.5][0 -0.5 0 0.5][0 0 0 1]` with the normalize bit (`0x100`). Signed 8-bit normals read with `/127` had length about 0.5, which showed the scale was wrong.
- Also found a pre-existing bit error: the code used bit 0 of `TexMtxInfo` as "projected" and bit 1 as the input form. Per the XF layout (checked in `reference/dolphin-source/Source/Core/VideoCommon/XFMemory.h`), bit 1 is the projection (ST/STQ) and bit 2 is the input form (AB11/ABC1).
- Implemented, following Dolphin's `VertexShaderGen.cpp`, `PixelShaderGen.cpp` and `VertexLoader_Normal.cpp`: normals decoded with the hardware fixed scale (u8 2^-7, s8 2^-6, u16 2^-15, s16 2^-14, float as is); raw (untransformed) normal as the texgen input, since the texture matrix carries the rotation; per-vertex texture matrix indices stored in `Vertex::texture_matrix`, defaulting to XF `0x1018`/`0x1019`; AB11 forces z to 1; for ST the third component is 1; dual transform normalizes when bit 8 of the post info is set and then applies the 3x4 post matrix at `0x500 + index*4`; the result is always divided by q, and q == 0 uses `clamp(xy/2, -1, 1)`. The division is per vertex, as before; Dolphin does it per pixel, so large projected triangles can still differ.
- The first attempt (the stash left by the previous session) rotated the normal by the position matrix and skipped the post matrix. It improved the look by chance. The real normal matrix at XF `0x400 + index*3` was checked with data and equals the 3x3 of the position matrix in the samples, but the hardware does not use it for texgen, so that path was dropped.
- Bisection with temporary environment switches (reverted): with the dual transform on but the old bit handling, the pink floor lines of the menu background vanished. They use the normal-based STQ material. With the correct bits and the Dolphin division they appear again.
- Verification: `cmake --build build/out`, `ctest --test-dir build/out` 3/3. Ran the scripted path (`WP_INPUT_SCRIPT` from `%TEMP%/wpcap/script.txt`, `build/out/wiiparty.exe extracted 115`, `WP_SAVE_FRAME`) and compared frames 10 (title), 26-45 (menus) and 53-57 (four Miis at the Board Game Island entrance) against the same run at `fe911a4`. Miis on the title and on the board now have light and shade. Menus and the rest of the path show no regression. Not checked against Dolphin frames; the face block artifacts were not checked at a higher resolution; no unit test was added because these functions are internal to `gx.cpp`.
- Intermittent crash found while testing, not caused by this change: `c0000005` with guest `lr=8000472c`, stack `fill_mem <- 0x80004714 <- 0x8017cd60 <- 0x80067410 <- menu module`. `0x8017cd60` (right after `WPADProbe`) reads the controller block from table `0x802b62d0[chan]` and queues HID report `0x15` (status request) into the queue at `block+0x164`. It is most likely `WPADGetInfoAsync`. `WPADInit` is replaced by an empty version, so the queue pointer is never set up. At `fe911a4` it did not show in 4 runs. ## Intermittent WPAD crash: WPAD state was never initialized (2026-09-22)

- Cause: `KPADInit` (`0x80193cf0`) was replaced by an empty function. The real `KPADInit` is what calls `WPADInit`, and the game never calls `WPADInit` directly (only `0x80065cf0` calls `KPADInit`). So the WPAD state was never set up: the control-block table at `0x802b62d0` stayed at zero and the blocks held whatever was in memory. About 13 SDK functions (`0x8017b7d0`, `0x8017b8c0`, `0x8017c2b0`, `0x8017cd60`, `0x8017d0d0`, `0x8017d7e0`, `0x8017ee70`, `0x8017f040`, `0x8017f320`, `0x801803a0`, `0x80180640`, `0x801817b0`, `0x80182da0`) queue commands through `block+0x164`; the one seen crashing was `0x8017cd60`, which cleared a queue entry through a garbage pointer.
- Identified `0x8017cd60` as `WPADGetInfoAsync(chan, WPADInfo*, callback)` in real Dolphin with `tools/dolphin_gdb.py` (`GDBPort = 2159` added to the user's `Dolphin.ini` after a backup and restored afterwards, byte for byte). The game calls it with channel 0, info `0x80728784` and callback `0x80067950`. The callback later receives `(0, 0)` from inside WPAD (`lr = 0x8017cd34`), so it is asynchronous. The info buffer then holds `dpd 0, speaker 0, attach 1 (Dolphin's emulated Nunchuk), lowBat 0, nearempty 0, battery 4, led 1, protocol 0, firmware 0`. The callback only sets a "ready" byte (`object+0xfbc`) when the result is 0.
- Also read in Dolphin: table entries `0x802b7300 + n*0xbe0`; each block's queue pointer (`+0x164`) is `block+0x16c`, capacity (`+0x168`) 24, indices at `+0x160`/`+0x161`. The original `WPADInit` (disassembled from the DOL with `recompiler/ppc/decoder.py`) initializes Bluetooth (`0x8018d250`) and, if that succeeds, calls `0x8017b310`. That function fills the table from `0x802b62a0 + 0x30` with blocks at `0x802b62a0 + 0x1060`, and for each channel calls the block reset `0x8017afd0` (memory only; sets status `+0x900 = -1`, "no controller", and sets up the queue) and `OSCreateAlarm` (`0x8013f780`). It then writes a hardware register (`0xcd0000c0`), reads system settings and runs callbacks, which were not reproduced.
- Fix in `engine/src/core/hle.cpp`. `WPADInit` and `KPADInit` now run the same per-channel loop as `0x8017b310`: set the 16 channel bytes at `+0x1040` to `0xff`, fill the table, clear `+0x8e8`, call the game's own `0x8017afd0` and `OSCreateAlarm`, and clear `+0xbae`. `WPADGetInfoAsync` is replaced (added to `games/wiiparty/analysis/symbols.csv` and `games/wiiparty/analysis/hle_functions.csv`). For a connected channel it fills `WPADInfo` (battery 4, LED `1 << chan`, no extension, since input is reported as a bare Wii Remote) and queues the callback with result 0 about 10 ms later, delivered with the IPC callbacks in interrupt context. For other channels it calls the callback at once with `-1` and returns `-1`, as the real function does on error.
- Verification: temporary logging (reverted) showed the four blocks set up with the same addresses as in Dolphin (queue `block+0x16c`, capacity 24, status `-1`) and `WPADGetInfoAsync` called twice per run with the callback delivered. `ctest` 3/3. The scripted path ran 8 times in a row with no crash, all reaching the Board Game Island entrance. Before the fix, about half the runs crashed with this build. The captured frames show the usual path and no new controller messages.
- The other WPAD functions still see "no controller" in their blocks (there is no Bluetooth), while `WPADProbe` and `KPADReadEx` report channel 0 as connected. Functions such as rumble (`0x8017cf80`) now return early instead of writing through garbage.

## Mipmaps and texture filtering as on hardware (2026-09-23)

- Before, every texture was created with one level, the shader always sampled level 0 (`SampleLevel(..., 0)`), and the sampler read only the low 8 bits of `TX_SETMODE0` with an old reading of the filter field. It turned on linear filtering if the magnification bit was set or if `(mode >> 5) & 7 >= 4`, so the separate minification and mip filters were ignored.
- Rules taken from `reference/dolphin-source` (`BPMemory.h` `TexMode0`/`TexMode1`, `RenderState.cpp` `SamplerState::Generate`, `TextureInfo.cpp`). `TX_SETMODE0` bits: 0-1 wrap S, 2-3 wrap T, 4 magnification linear, 5-6 mip mode (none, point, linear), 7 minification linear, 9-16 LOD bias (signed, 1/32). `TX_SETMODE1`: min LOD bits 0-7 and max LOD bits 8-15 (1/16). Mipmaps are on when the mip mode is not zero. The level count is `min(log2(max(w, h)) + 1, (max_lod + 15) / 16 + 1)`. Each level is `max(size >> n, 1)`, padded to the format's block size, and stored right after the previous one in RAM. With no mipmaps, min and max LOD and the bias are 0.
- `texture_for` in `engine/src/gpu/gx_render.cpp` now decodes all levels (stopping early if memory runs out), hashes all of them and creates the D3D11 texture with that many levels. The cache key includes the level count. `sampler_for` uses the three filters and the LOD registers, and its key now covers `TX_SETMODE0` bits 0-21 and `TX_SETMODE1`. The pixel shader takes the derivatives of the eight texture coordinates before the TEV loop and samples with `SampleGrad`, since implicit-derivative sampling is not allowed inside the loop. EFB copy textures keep one level.
- Verification: `ctest` 3/3, 50 fps on the title screen (`WP_LOG_FPS`). The shader compiles, and the scripted path to Board Game Island runs to the end. Temporary logging (reverted) showed that only 3 of about 640 textures created on that path ask for mipmaps (128x128, 64x128 and 32x32 IA8, with 3 to 7 levels; one has a LOD bias of -1.94). So the visible change on that path is small: the frames differ from the previous build only through animation timing and the randomly chosen Miis. The corrected minification and magnification filters apply to all textures. The minigames and the board, where distant geometry is more common, have not been checked yet.

## Board freeze solved: single-precision results did not fill the second paired-single lane (2026-09-23)

- Traced with temporary probes (reverted) in the generated `build/recomp/dol_003.cpp` (rotation setters) and `build/rel_code/mr001_002.cpp` (Board Game Island). ## Crash when a minigame loads: a reused thread slot resumed the previous, finished thread (2026-09-23)

- Symptom (reported by the user playing manually, and reproduced with the scripted path): at the start of the second round, often right after `TARZAN ACTION`, the game aborted with `thread function 800354b0 returned without exiting (exit function 8013ffd0)`. `0x800354b0` is a short loader thread (it calls `0x80169f30` and `0x801379a0`, then sets bit `0x20` at `+0x378` of its object) that the game creates again and again in the same `OSThread` structure. `0x8013ffd0` is `OSExitThread`, which must never return.
- Cause: `engine/src/core/threads.cpp` maps each saved guest context to the Windows fiber that saved it. If a decrementer interrupt arrived while the loader thread was exiting, `deliver_decrementer` saved `OSCurrentContext` (still that thread's context) with the dying fiber. The next time the game created a thread in the same structure (`OSCreateThread` -> `OSInitContext` writes the new entry point into SRR0), `load_context` found that old entry and resumed the dying fiber instead of starting the new thread. That fiber came back into `OSExitThread`, which returned.
- Fix: a saved context now records the resume address it wrote to SRR0. If SRR0 no longer matches when the context is loaded, the context was reinitialised; the stale fiber is discarded (its saved entries removed and the fiber deleted, unless it is the running one) and a new fiber starts the new thread. This also frees some finished fibers.
- Verification: a temporary message in the discard path showed it firing twice right after `TARZAN ACTION` in a 570 s scripted run, which then went on into the second round with no abort (the run ended at the watchdog on the Chop Chops instruction screen, where the scripted A press at a fixed position did not start the minigame; not yet checked by hand). `ctest` 3/3.

## Audio, phase A: timing model of the audio pipeline (2026-09-23)

- Symptom: the first audio build sounded very bad to the user. Method: `WP_DUMP_AUDIO` recordings compared sample by sample with Dolphin's own dump (`[DSP] DumpAudio = True` in `Dolphin.ini`, enabled for one run and restored byte for byte), plus temporary per-cycle timelines (removed afterwards). The DSP output itself was correct: once timing was fixed, 16-24 s of title music matched Dolphin sample for sample. Every problem was scheduling in `engine/src/audio/dsp.cpp`.
- Findings, in order:
  1. 56% of the 3 ms AX buffers (96 frames) were played twice. The DSP thread slept with `std::condition_variable::wait_for`, which in this MinGW runtime sleeps 10-15 ms even with `timeBeginPeriod(1)`; the audio DMA then consumed several buffers in a burst while the game had set up only one. Fixed with Win32 events (`WaitForSingleObject`, 1 ms).
  2. The CPU spent much of its time in `0x8016a1e0` (the SDK loop that waits until the DSP has read a mail) because the DSP only ran about once per millisecond. As in Dolphin (`DSP_MAIL_SLICE`), a CPU read of a mailbox that is waiting now runs a short DSP slice (512 cycles) on the CPU thread, without blocking if the DSP thread already holds the core. The DSP thread sleeps when the DSP is halted or sits at an idle-skip address from Dolphin's analyzer, instead of spinning.
  3. The DSP runs at 4x the hardware clock (486 MHz of DSP time per second at most). Running early is invisible to the game (the microcode waits for mail), and it absorbs the extra handoff latency between host threads. At 1x the pipeline only reached 75% of real time.
  4. The audio DMA runs on its own thread with an exact schedule: each 32-byte block is due `8 / rate` seconds after the previous one, from timestamps, so the thread's wake-up granularity never loses time. An earlier counter-based version dropped about 0.5 ms per buffer (3.49 ms per 3.0 ms buffer).
  5. When a buffer ends, the DSP interface raises the audio DMA interrupt and asserts the interrupt line by setting `g_poll_counter` to `kPollInterval`, so the CPU checks interrupts at its next loop branch instead of up to 16,384 branches later.
- Model (the only two deviations from the hardware, both compensating for the CPU taking interrupts later than a real Broadway): (a) the next buffer is latched only once the game has written a new start address (on hardware the old address would be reused, which here replayed stale buffers); (b) a latched buffer starts only after the game acknowledged its interrupt, but it keeps the ideal schedule, so a late acknowledgement is caught up and real time is kept. Measured over 591 cycles in the menu: 334 buffers per second (hardware 333.3), no drift, the game writes the next address 0.08 ms after each start, and the median acknowledgement latency is 0.01 ms (95th percentile 1.9 ms).
- Measured alternatives, for the record: without (a) and (b) 19% of buffers repeat; (b) resetting the schedule at the acknowledgement kept the output identical to Dolphin but reached only 62-78% of real time; only (a) gave 86% of real time and 97.6% identity. A separate DMA thread alone changed little (66% -> 68%); moving GX work out of `GXDrawDone` into the interrupt poll did not help either, and delivering interrupts from inside GX processing crashed the game (thread switches inside native code) and was reverted.
- Result: title music 99.76% identical to Dolphin over 24.5 s (the remaining differences are the last ~30 samples of about two buffers per second, read before the DSP finished writing them after a late acknowledgement), no repeated buffers, 50 fps on the title, menu and board. `ctest` 3/3.

## The DSP runs in lockstep on the CPU thread; timestamped diagnostic log (2026-09-23)

- Problem: entering the main menu from the title dropped to 7-18 fps for about 2.5 s. Profiling the window showed the CPU inside the audio DMA interrupt handler (`0x8015e750`), blocked on the DSP core mutex while the DSP thread was busy. A CPU read of a waiting mailbox still runs a 512-cycle DSP slice (charged to the same budget). There are no mutexes or events left in `engine/src/audio/dsp.cpp`; the WASAPI thread in `engine/src/audio/audio.cpp` only shares the sample queue. The DSP clock multiplier went back to 1x.

## Audio, phase B (first step): the AX microcode is recompiled to C++ (2026-09-23)

- The AX microcode (8 KB, 4096 words) is stored whole in the DOL at file offset `0x21ffc0` (found by dumping the IRAM image with `WP_DUMP_DSP_CODE=dir` and searching the DOL). `games/wiiparty/analysis/dsp_ucode.csv` records the name, offset, size and checksum; the microcode itself is never committed. A profile of the interpreter (temporary) showed 57% of steps in the 3-instruction mail wait loop at `0x0051` (idle time) and the real work spread over about 1,300 addresses, so the whole IRAM is translated.
- `recompiler/dsp/tables.py` reads Dolphin's own opcode templates and interpreter handler tables from the C++ sources, and decodes exactly like the interpreter (first matching entry, 7-bit extension for `0x3xxx` opcodes). `recompiler/dsp/recomp_dsp.py` finds instruction starts and hardware loop ends the same way as Dolphin's `Analyzer::FindInstructionStarts`, and writes `build/dsp_recomp/ax.cpp` plus a registry keyed by checksum. Each instruction becomes a label that checks the cycle budget, checks pending exceptions, sets the fetch pc, calls the extension handler, the main handler and `ApplyWriteBackLog` with the opcode as a constant, and falls through to the next instruction unless the pc changed; loop ends call `HandleLoop` only where the analyzer marks them; any pc change goes to a `switch` dispatcher, which also stops at idle-skip addresses. When an exception is taken, the handler's first instruction runs in the same step, as in `Interpreter::Step`. Addresses outside the translated starts (and the ROM) fall back to the interpreter.
- `engine/src/audio/dsp.cpp` picks the translation when a microcode with a known checksum is uploaded (`WP_DSP_INTERPRETER=1` forces the interpreter). A DSP slice now charges only the instructions it actually executed; charging a fixed 512 cycles per mailbox read starved the DSP once it ran faster.
- Verification, `WP_DSP_VERIFY=1`: each translated run is replayed on the interpreter from a snapshot of the whole DSP state (Dolphin's `DoState`, with a real byte-vector `PointerWrap` in the shim), undoing the translated run's writes to console memory first, and both the DSP states and the memory write sequences are compared; on a mismatch it searches the first diverging instruction. It found two real bugs, both fixed: the budget was only checked at branches (fixed by checking it per instruction) and an exception taken at the end of the budget counted a step without running the handler's first instruction. Result: 0 mismatches in 320,000 runs over 150 s of title, menu, board and minigames. An earlier batch of "mismatches" were false positives from not undoing the DSP's memory writes before the replay.
- Performance (`WP_LOG_FILE`): the DSP uses about 14% of the CPU thread in the menu (interpreter: 21%) and 57-59% while the menu loads (interpreter: 68-70%); the longest frame when entering the menu is about 140 ms (interpreter: 221 ms). Title music: 99.5-99.9% identical to Dolphin, against 99.98-100% with the interpreter; since the two engines execute identically, the difference is timing (buffer tails read before the DSP finished writing them), not translation.
- Next: emit the hot instructions (multiply, add, parallel loads and stores) inline instead of calling the interpreter handlers, and model when the audio DMA may read a buffer relative to the DSP's writes so the last buffer tails match too.

## Audio, phase B (second step): inline DSP code, lazy flags, static branches; audio DMA catch-up limit; title bar telemetry (2026-09-24)

- Inline code: `recompiler/dsp/inline_ops.py` emits, for 64 main opcodes and all 25 extension opcodes, the statements of the matching Dolphin interpreter handler with the operand fields decoded at generation time, over helpers in `engine/include/wp/dsp_inline.h` (register access with the 40-bit mode saturation, stacks, address register wrapping, accumulator/product arithmetic, multiplier modes, status register updates, condition codes). Extension opcodes keep the interpreter's order: their reads and stores happen before the main operation and their register writes after it. Branches (`jcc`, `call`, `ret`, `jmprcc`, `ifcc`, `loop`, `loopi`, `bloop`, `bloopi`) and the hardware loop end (`HandleLoop`) are emitted inline too; a taken branch or loop jump goes straight to the target label when the target is a translated instruction start, is not an idle-skip address and its previous address is not a loop end (the same checks the dispatcher makes). The idle-skip addresses are computed the way Dolphin's `Analyzer::FindIdleSkips` does, reading its signature table from `DSPAnalyzer.cpp`; checked at run time against the analyzer (the same 9 addresses and 88 loop ends). 2,887 of the 3,011 instructions are inline; the rest still call the interpreter handlers.
- Lazy flags: an instruction whose status flags are overwritten by a later instruction in straight-line code before anything reads them (no status register access, no branch, no loop end in between) stores the result, carry and overflow in locals instead of computing the flags (321 instructions). The flags are computed only if the translated code is left in between (end of the cycle budget or a pending exception); the sticky overflow bit is still set at once. Each instruction's budget and exception checks were merged into one branch with a cold path.
- Verification: `WP_DSP_VERIFY` 0 mismatches in 340,000 runs over 170 s. A deliberate bug (flags not computed on exit) was caught at once, so the checks do cover the lazy flags.
- Performance: DSP cost per cycle (DSP time over DSP cycles in `WP_LOG_FILE`) from 14.1 ns to 3.1 ns; the DSP's share of the CPU thread in the menu from about 7% to 1.7% (sampling profile), peak share while the menu loads from 72% to 3-13%. Every differing sample equalled Dolphin's output 192 samples (two 3 ms AX frames) earlier: the audio DMA played a buffer before the DSP had written the new frame into it. A temporary trace of buffer latches, starts, CPU mails and DSP output writes showed the cause: every frame (20 ms) the CPU thread spends 4-12 ms in graphics processing without polling interrupts; afterwards the audio DMA, which keeps the ideal schedule, played the missed buffers in a burst of a few tenths of a millisecond, faster than the chain audio interrupt -> CPU -> mail -> DSP (about 0.3 ms per frame) could refill them. A faster DSP made the burst shorter, hence the drop (the interpreter, slower than real time, spread it out). Tried and rejected: running a mailbox slice only when the DSP has budget (as Dolphin does with `DSP_MAIL_SLICE`) made it worse (92%); giving the DSP back the acknowledgement latency helped (98%) but did not fix it. Kept: the audio DMA advances its own clock at most 4 times as fast as real time (and at most 0.5 ms per call after a pause), so after a pause it catches up in about a third of the pause and the refill chain keeps up; the long-term rate is still exact. Result: the title music is identical to Dolphin sample for sample over the whole 31.7 s reference, in every run (0 of 1,013,950 frames differ); with the interpreter 112 frames still differ (it is slower than the real DSP at the busiest moments). Moving graphics processing off the CPU thread remains the real fix for the pauses.
- Title bar (PC enhancement, `engine/src/platform/video.cpp`): `Wii Party (SUPP01) | Direct3D 11 | PAL | FPS: 50 | DSP: NATIVE (2%)`, updated once per second from the frame counter in `engine/src/gpu/gx.cpp` and `dsp::status()` (`NATIVE` recompiled, `INTERP` interpreter, `OFF` before any microcode; the boot microcode of the OS runs on the interpreter for the first seconds). ## Mii faces in House Party: EFB clears follow the update masks (2026-09-24)

- Symptom (reported by the user): in House Party screens, and on the House Party panel of the main menu, the Mii faces changed between runs, with solid black eyes and mouths or a pale "ghost" look; the same Miis looked right on the Start game screen.
- Diagnosis with temporary logging and dumps of the EFB copies (removed afterwards): all copies were found by the texture lookup (no misses), so the problem was in what they contained. For each face the face library draws the features twice into a 128x128 EFB region and copies both times to the same address, with the copy's clear bit set: pass A writes color and alpha and is copied; at that copy the blend mode already has color updates off and alpha updates on (`0x41 = 0xf7d0`); pass B writes alpha only and is copied again, and that second copy is the texture used. Our `render::clear()` always cleared color, alpha and depth of the whole EFB, so pass B found a black EFB and the final face texture was black with the right alpha. The Miis differ between runs (random guests), which made it look erratic.

## DSP: random-state test of every recompiled instruction and verifier coverage (2026-09-24)

- Why: `WP_DSP_VERIFY` only checks what the game happens to execute. Its new coverage count shows how little that is: after 2 minutes of title and menu, 990 of the 3,011 instructions of the AX microcode had been checked (32%).
- `WP_DSP_SELFTEST=N` (`engine/src/audio/dsp.cpp`): when the recompiled microcode is loaded, every instruction start runs N times from a random state (registers, accumulators, product, status register including the 40-bit and multiplier modes, loop registers, DSP data memory; address registers point to data or coefficient memory) with budgets of 1, 2, 3 and 8 instructions, and each run is compared with Dolphin's interpreter through the same code as `WP_DSP_VERIFY` (whole DSP state plus the sequence of writes to console memory). The budgets of 1 cover every exit with deferred flags; the longer ones the paths where the flags are overwritten, the branches and loop ends. It runs on its own thread (64 MB stack), restores the DSP state and interrupt bits afterwards, prints a summary and exits with 0 or 1.
- What it found and fixed:
  1. Dolphin's `SDSP::DoDMA` calls `std::exit(0)` when a DSP DMA is longer than 0x4000 bytes; random states hit it and the process closed silently. It now ignores such a DMA.
  2. DSP DMAs with random registers wrote past the 4096 words of DSP memory (Dolphin passes `dram + dsp_addr / 2` without a bound) and read outside console memory. `DMAToDSP`/`DMAFromDSP` now stop at the end of the DSP memory array and map the console address like the accelerator does (MEM1 or MEM2 mask).
  3. Runs where the microcode copies new code into its own instruction memory (DMA to IRAM with random control bits) cannot be compared with a static translation. They are now detected (the IRAM DMA path calls `CodeLoaded`) and counted apart; in `WP_DSP_VERIFY` during the game such a run would be reported. Restoring a snapshot no longer goes through `CodeLoaded`, which also removes a code analysis per verified run (the verifier went from about 3,000 to 18,000 runs per second).
  4. The only real difference was in the reference: in unsigned multiplier mode Dolphin's `GetMultiplyProduct` computed `static_cast<u32>(a * b)`, a signed `int` multiplication that overflows for large operands (undefined behaviour). Built with `-O2` (since yesterday), GCC produced a sign-extended product (`prod.h = 0xff`) where the recompiled code gave the intended unsigned value. Fixed in the copy of Dolphin as `static_cast<u32>(a) * b`.
- Result: `WP_DSP_SELFTEST=100`: 1,204,400 random runs over all 3,011 instructions, 0 mismatches (11,664 runs skipped because they overwrote the instruction memory), in 43 s. `WP_DSP_VERIFY` during 2 minutes of play: 2.2 million runs, 0 mismatches. Title music against Dolphin: 3 of 4 runs with 0 differing frames of 1,013,950; one run had one late half buffer (48 frames, the 192-sample stale pattern of the audio DMA timing), not a DSP difference. `ctest` 3/3.
- Limits: the reference is still Dolphin's interpreter (identity with Dolphin, not a proof against the hardware), and instructions that read hardware registers depend on the device state in the snapshot, which is not randomised.

## Menu entry stall: no artificial IPC latency (2026-09-24)

- Measurement (`WP_LOG_FILE`, scripted path, three runs): entering the main menu gave a 67 ms frame while the `loading` module ran and a 102-107 ms frame 0.7 s after the `menu` module loaded, at the same times in every run.
- A sampling profiler with timestamps (temporary, outside the repository) showed the CPU thread 37% idle in `OSSelectThread` during the 105 ms frame, so the frame was waiting, not working. The disc log showed about 80 reads in 60 ms: the game reads a compressed file, decompresses it with the SDK's LZ routine (`0x80169f30`), and asks for the next one, and the frame waits for the chain. Every asynchronous IPC completion was delivered at least 1 ms late (`kIpcLatency` in `engine/src/core/hle.cpp`), a delay added earlier as "more realistic" and recorded at the time as not the cause of anything. It is not realistic either (a real disc drive is much slower; here the files come from the hard disk at once), so completions are now delivered at the next interrupt check.
- Result: the 67 ms frame is gone and the 105 ms frame is 59-64 ms. A profile with stack walking of what remains: the game's LZ decompression (about 18%), graphics processing of the first menu frame with many new models (about 25-30%), and file reads (about 7%; opening, reading and closing the files costs 4.4 ms in total). On a Wii, decompressing about 1.5 MB with its 729 MHz CPU and reading from the optical disc would make this frame slower, so what remains is the game's own loading; moving graphics processing off the CPU thread would hide part of it.
- Verified: the scripted path to Board Game Island for 200 s (explanation, the Flag Fracas minigame, results and play order) runs with no hang; `ctest` 3/3.

## Audio output: buffer level control and fades (2026-09-24)

## Audio: stale buffer detector (2026-09-24)

## GPU draw-done interrupt and graphics on their own thread (2026-09-24)

- Why: the stale buffer detector showed 20-170 late audio blocks per second in minigames, with 200-300 of the 333 audio buffers per second acknowledged more than 1 ms late, because the CPU thread spent 4-12 ms per frame processing graphics without polling interrupts. On the Wii the GPU is a separate chip that works in parallel.
- `GXDrawDone` is no longer replaced (`games/wiiparty/analysis/hle_functions.csv` now has 12 entries). The game's own function (decompiled with `tools/ghidra_decompile.py`) writes BP `0x45` with bit 1 (draw done) to the FIFO, then sleeps the thread until the PE finish interrupt handler (`0x801501f0`, OS interrupt 19) sets a flag and wakes it. `engine/src/gpu/gx.cpp` now raises that interrupt when it processes the draw-done command, and `poll_interrupts` delivers it through the game's handler like the other external interrupts (`deliver_external_interrupt`). While the game thread sleeps, the CPU runs other threads or the idle loop and keeps answering interrupts.
- GPU thread (`engine/src/gpu/gx.cpp`): the CPU thread still collects FIFO writes; at every interrupt check (and when 1 MB accumulates) it hands them to a GPU thread, which parses them, draws with Direct3D 11, raises the draw-done interrupt, and presents the frame when it reaches the present request queued at the video retrace (`gx::run_frame_task`; `engine/src/platform/video.cpp` runs `present_frame` and `WP_SAVE_FRAME` there). The CPU never gets more than 2 frames ahead of the GPU. Only the GPU thread uses the Direct3D device. The values the title bar reads from the DSP are atomics. `WP_GPU_THREAD=0` keeps the old single-thread processing.
- Intermediate measurement, single thread with the new interrupt: processing the FIFO inside every interrupt check made the minigame worse (31,382 stale blocks in 38 s; 5,846 when processed at the end of the check), which confirmed that the fix had to take the work off the CPU thread.
- Result (200 s scripted path, whack-a-mole style minigame): 0 stale audio blocks in the minigame (before: about 2,500), late buffer starts from about 9,500 to 663 in 38 s, 50 fps throughout, images unchanged on title, menus, island and minigame. Title music identical to Dolphin in two runs. `WP_GPU_THREAD=0` still runs at 50 fps. `ctest` 3/3.
- Not done: the CPU does not read PE token or FIFO status registers from the GPU thread (the game has not needed them so far); EFB peeks are not emulated.

## Clip-space vertices: triangles crossing the camera plane are clipped, textures perspective-correct (2026-09-24)

- Symptom: in the Flag Fracas beach minigame part of the ground was black and cut diagonally. Cause in `engine/src/gpu/gx.cpp`: every vertex was projected and divided by w on the CPU, and a triangle with any vertex behind the camera (w <= 0) was dropped whole, so large ground and sky polygons that pass under or behind the camera disappeared. Sending already-divided screen positions also made the GPU interpolate colors and texture coordinates without perspective correction (affine), which warps textures on large polygons.
- Change: `project` now outputs homogeneous clip coordinates (x, y, z, w) with the GX viewport folded in (x' = x * 2 sx / 640 + w * (2 (cx - 342) / 640 - 1), the same for y with the sign flipped, z' = (z * sz + w * cz) / 16777215), `ScreenVertex` has a `w`, the vertex shader passes the position through, and Direct3D clips at the camera plane and interpolates with perspective correction. Depth is still clamped to [0, 1] per pixel (depth clip is off, as before per vertex). Face culling uses the determinant of the three (x, y, w) rows, whose sign equals the screen-space orientation and stays valid for vertices behind the camera. A vertex is invalid only if a coordinate is not finite.
- Verified: the scripted path (menus, island, explanation, the Feathered Frenzy minigame) draws as before, with no missing geometry, at 50 fps; `ctest` 3/3. The beach minigame did not come up in this run (the minigame is random), so the black ground is expected fixed from the cause but not yet seen.

## TEV with the hardware's integer arithmetic (2026-09-24)

- The TEV ubershader (`engine/src/gpu/gx_render.cpp`) computed in floating point. It now follows the hardware's integer pipeline as documented by Dolphin's `PixelShaderGen.cpp`: inputs a, b and c are 8-bit, d is signed; each stage computes `((d + bias) << scale) +/- ((((a << 8) + (b - a) * (c + (c >> 7))) << scale) + round) >> 8` with a rounding term of 128 (add) or 127 (subtract) except when dividing by 2, clamps to 0..255 or to the signed 11-bit range, and the compare modes work on the 8-bit values. Constant selections use the hardware table (255, 223, 191, 159, 128, 96, 64, 32; invalid selections give 0), textures and rasterized colors are rounded to 8 bits, and the final color wraps modulo 256 instead of saturating. Differences against the float version are 1-2 levels at edges and gradients.

## Indirect textures and fixed-point texture coordinates (2026-09-24)

## Blending rules of the hardware (2026-09-24)

## IPC hardware instead of the IOSSendRequest replacement; first boot without a save (2026-09-24)

- Problem: with an empty `games/wiiparty/nand` (first run, no save), the game stopped with a black screen right after creating `wiiparty.bin` and `banner.bin`. Two causes were found.
- Cause 1: `IOSSendRequest` (`0x80175af0`, the SDK's `__ios_Ipc2`) was replaced by a runtime handler. The original frees the request itself on the synchronous path (`iosFree` at `0x80175d30`); the replacement did not, so every synchronous request leaked 0x40 bytes of the IPC heap. With a save present there are few of them; creating the save used enough of them to exhaust the heap, and `IOS_IoctlvAsync` returned -22 (out of memory, `iosAllocAligned` at `0x80176b14`) on the Bluetooth driver (`__IntrBlkMsgInt: IoctlvAsync returned error -22`).
- Cause 2: the menu module creates the save on its own thread (`f_menu_010585c0`, priority 30). That thread sets the flag at `r13-0x75b6` to 1, works, and sets it back to 0; the main thread waits first for the 1 and then for the 0 (`0x1058d9c`/`0x1058db8`). On a console every NAND operation takes milliseconds (a superblock write is about 52 ms) and the thread sleeps waiting for the reply, so the main thread always sees the 1. Here synchronous IPC requests returned at once, the whole thread finished inside one frame and the main thread waited forever.
- Fix, following the fidelity rule (the hardware is emulated, the SDK code runs translated): `IOSSendRequest` was removed from `games/wiiparty/analysis/hle_functions.csv` (11 runtime handlers remain) and the IPC hardware is emulated in the new `engine/src/ios/ipc.cpp` (registers `PPCMSG`, `PPCCTRL`, `ARMMSG`, `PPC_IRQFLAG`, `PPC_IRQMASK` at `0xCD000000`, reached through `rd32`/`wr32` in `engine/include/wp/memory.h`). A write with X1 queues the request 500 timebase ticks later; when the interface is free, IOS acknowledges (Y2), runs the command in `engine/src/ios/ios.cpp` and schedules the reply after the command's latency (the reply writes the result at `+4`, the original command at `+8` and 8 at `+0`, as IOS does); replies are kept in order; Y1/Y2 raise interrupt 27 (`__IPCInterruptHandler`, `0x801757f0`, registered by `IPCCltInit`) 100 ticks later. The SDK's own code now queues requests, sleeps the calling thread on synchronous requests (`OSSleepThread(request + 0x2c)`), wakes it, calls callbacks and frees requests. `ipc_pending`/`ipc_deliver`, the request freeing done by the runtime and `ios::never_completes` were removed: the STM event hook simply never gets a reply, as on real IOS.
- Latencies (from Dolphin's measurements for IOS 56, see `THIRD_PARTY_NOTICES.md`): 2700 ticks of IPC overhead for `/dev/fs` and NAND files, 4000 for other devices; path lookups; superblock writes for create, delete, rename, successful directory creation and closing a written file; cluster reads and writes with IOS's one-cluster cache simulated as Dolphin does. `/dev/di` still answers with the default 4000 ticks, not with drive timing. Bluetooth replies that were deferred are sent when their data exists.
- `ISFS_GetUsage` (`/dev/fs` ioctlv 0x0C) returned success without writing its two outputs; it now counts the used clusters (16 KB, rounded up per file) and inodes (the directory itself plus every entry) of the host directory, and returns -106 or -101 for a missing path or a file. The SDK's NAND check calls it for `/meta`, `/ticket`, `/title/0001000x` and `/shared2/title`.
- `/dev/es` ioctlv 0x16 (`GetConsumption`) and 0x1B (`DIGetTicketView`) returned success without writing anything. Now that the SDK builds these requests with its own buffers, stale data made `OSPlayTime` stop with `PANIC in OSPlayTime.c on line 737: Expired`. They now report no consumption records and a zeroed ticket view (no play-time limits).
- Verified: with an empty NAND the game creates `wiiparty.bin` and `banner.bin`, reaches the title screen and, with A+B held (`WP_INPUT_BUTTONS=C00`), the main menu; with the save present it boots as before; the Wii Remote handshake (IR camera, report modes) completes. `ctest` 3/3. The title screen now appears about 2 s later on the first boot, because the NAND takes the time it takes on a console. The full scripted path to Board Game Island was not rerun (the user is testing a full game by hand).

## Time base overflow after five minutes: black screen after "Round 2" (2026-09-24)

- User report: the game stayed on a black screen after "Round 2". Reproduced with a scripted board game: at about 305 s the rendering stopped and no IPC request (disc, Bluetooth) was sent any more; the main thread slept in the DVD library (`0x8015a7f0`) and another thread waited on a mutex.
- A new IPC report in the watchdog dump (`ipc::report`: control, flags, queues, pending events and a trace of the last 64 register accesses, acknowledgements and replies) showed pending replies due about 227 s in the future and a trace whose older entries were later than the newer ones: the guest time base had jumped back.

From then on the time base went back by about 303 s, so every alarm, the decrementer and the IPC reply schedule broke. The elapsed time is now split into whole seconds and the remainder before scaling.
- Verified: the same scripted game now runs past 450 s at 50 fps, through "Round 2" and "Round 3" and the Hammer Heads minigame with its results; the IPC report at the end shows nothing pending. The scripts used for long runs now tap A while not pointing (the board ignores A while the pointer is on screen) and sweep the pointer over a 5x4 grid so minigames that start by pointing at the player's Mii also begin.

## Audio micro-cuts on busy board scenes (2026-09-24)

- User report: short audio cuts and background noise, mostly while rolling after winning a minigame (the "Double!" scene with the cheering crowd).
- Measured on a scripted board game with `WP_LOG_FILE`: (1) during the load of a minigame the CPU thread stopped for up to 365 ms (a 797 ms slow frame, 96 stale audio blocks, audible gaps in the output); (2) on busy board scenes (about 2 million vertices per second) about 80 DSP audio frames per second started late, up to 7 ms, and a few blocks per minute were played before the DSP had written them.
- Cause of (1): the video interrupt hands the frame to the GPU thread (`run_frame_task`), and when that thread was two frames behind (new textures while a scene loads) the CPU thread waited for it without limit, inside the interrupt, so neither the DSP nor the game's audio interrupts ran. On the console presenting a frame never blocks the CPU. Now, when the GPU thread is two frames behind, that presentation is skipped (the previous image stays on screen) and the CPU continues; the game's own `GXDrawDone` waits still pace it against the GPU, as on hardware. The `fps` log line counts skipped presentations.
- Cause of (2): the translated code checks for interrupts, the DSP and the audio pump every 16,384 loop back-edges, which on busy scenes meant up to 7 ms between checks. The counter now counts down (same cost per check) and the interval can be set with `WP_POLL_INTERVAL`. Measured on the same 260 s run: 16,384 gave 4284 late starts, 18 stale blocks, worst 6.9 ms; 4096 gave 1652, 0, 4.3 ms; 1024 gave 359, 0, 2.6 ms, with the same frame rate in all three (minimum 41-43 fps in the heaviest second). The default is now 1024.
- Verified: after both changes the output log shows no missing frames and no trims after the start, and there are no stale blocks. `ctest` 3/3.

## Coroutines resumed at any return address: Hurdle Hover crash fixed (2026-09-26)

- Reproduced with a scripted Free Play run (menus to "Obstáculos rodantes" / Hurdle Hover, then no input): at the end of the race the game always stopped with `call to unknown function 0100172c`. Temporary logging (removed) showed the sequence. `mg405` keeps a task's context at `+0x10`; the scheduler (`0x01001640`) jumps into it while the finished flag at `+0x198` is 0; the yield (`0x01001710`) saves it with `setjmp`. One task's body returned without yielding again and without setting the flag, so the scheduler jumped once more into the context of its last yield, which had already been resumed. On the console that works: the guest stack still holds the frames (`yield -> 0x0101b3a0 -> 0x0101b0ec -> entry 0x010016c8`, checked in memory at the failure), so the task simply runs the tail after its last yield again and ends. The translated code could only resume a `setjmp` whose native frame was still alive, or start a fresh function.
- Change: the translator now records a resume point after every call (`bl`, `blrl`, `bctrl`, `setjmp`, `OSSaveContext`) and emits an `R_<address>` label there, with a prologue that jumps to it when `wp::g_resume_address` is set (a single global test on function entry). `function_table.cpp` gets `g_resume_table` (30,163 points in the DOL) and each module descriptor its own resume list. When a `longjmp` targets a context with no live `setjmp`, `start_jump` (`engine/src/core/threads.cpp`) looks the link up: a function entry is called as before; a resume point is entered with `r3` set to the jump value, and when that function returns, execution continues at the guest link register, the caller's return address, until the chain ends. Everything the continuation needs lives in guest memory and registers, so this follows the hardware exactly. Module links are synthetic addresses; they are matched against the resume lists of the loaded modules, and an ambiguous match is reported.
- Verified: the same scripted run now ends the race and shows the results screen; `ctest` passes (a new test checks the resume points and prologue). All modules and the DOL were regenerated and rebuilt. The user then played 35 minigames in Free Play with this build with no crash (see `docs/MINIGAMES.md`). The scripted Board Game Island path was not rerun.
- Diagnostics: the `WP_LOG_FILE` log gains a `threads` line every second: busy share of the CPU thread and the GPU thread, and the share of samples in which the guest is idle in `OSSelectThread`. In Hurdle Hover it shows about 41 fps with the guest idle 57% and the GPU thread busy 67%: neither is saturated, the game waits for the GPU at the end of each frame (`GXDrawDone`), and the GPU thread needs about 16 ms per frame for about 60,000 vertices. Speeding up vertex processing is the next step.

## Automatic save backups (2026-09-26)

- The save lives in the virtual NAND at `title/00010000/<title ID low>/data` (the low half is the game ID at `0x80000000`, as `/dev/es` reports it; Wii Party writes `wiiparty.bin` and `banner.bin` there). New `engine/src/platform/save_backup.cpp` (`wp/save_backup.h`; `std::filesystem` with `error_code` overloads, and no exception leaves it) lists, checks, copies, rotates and restores backups. The launcher compiles the same file, so the engine and the launcher cannot disagree.
- `wp::nand::mount` (`engine/src/ios/nand.cpp`), which runs before the game's first instruction, copies the save to `games/wiiparty/backups/<YYYY-MM-DD_HH-MM-SS>/title/00010000/<id>/data/` when it differs (file list and bytes) from the newest backup, then deletes the oldest backups beyond `saves.backups` (default 5, 0 turns backups off; `WP_SAVE_BACKUPS`). The copy goes to `<name>.partial`, is compared with the save and only then renamed, so an interrupted copy never looks like a backup; two backups in the same second get `_2`, `_3`.
- After the game writes the save: closing a NAND file that was written inside the save folder, or renaming something into it, makes another backup, at most one per minute and only when no save file is still open for writing; a change inside the minute is taken at the next NAND file close after it, or at the next start.
- Check: before a backup every save file must open and read back completely at its size. The code visible here does not show a fixed save size (the files are created empty by `ISFS_CreateFile` and then written), so no size is checked. On failure the engine prints `save backup (...): ... failed the check: ...` and makes no backup, so rotation cannot push out the good ones; nothing is restored automatically. The engine never deletes or moves the live save.
- Launcher: a new **Saves** page (`Partidas` in Spanish) lists the backups by date with their size, a Restore button behind a confirmation dialog, and Open folder. Restore backs up the current save first (without rotation), copies the backup next to the save (`data.restoring`), swaps the folders by renaming, rolls back on failure and rotates at the end; a current save that fails the check is moved to `backups/damaged-<date>/` instead of being deleted. The Settings page shows the backup count under Saves.
- Verified: engine and tests cross-built with MinGW with no new warnings; `runtime_tests.exe` under Wine passes, with new tests in a temporary folder for a missing save, a first backup, an identical save not duplicated, two backups in the same second, rotation to 3, restore (the current save backed up first, the restored files in place, no leftover folders), restoring an identical backup, and an empty backup refused. The launcher was built natively on Linux and its Saves page captured with `--screenshot` offscreen in English and Spanish, with three sample backups and with none. Not run with the game (the game cannot be built here): the start backup and the backup after the game saves have not been seen on a real save, and Restore was not clicked in a real window.

## Custom textures: dumping and loading with Dolphin's names (2026-09-26)

- `docs/FEATURES_QOL.md` 1.3 asks for high-resolution textures. They are replaced by content, in the engine's renderer, the way Dolphin does it, so existing Dolphin packs for Wii Party (`SUPP01`) can be used. New `engine/src/gpu/custom_textures.cpp` (`wp/custom_textures.h`): XXH64 (written from the public algorithm; `third_party/dolphin` has no xxhash), the name `tex1_{w}x{h}[_m]_{texture hash:016x}[_{palette hash:016x}]_{format}` with the `_$` palette wildcard and `_mipN` levels, the palette range rule (for C4, C8 and C14X2 only the entries between the lowest and the highest index present in the level 0 data are hashed), an index of the PNG files under a folder and its sub-folders (keys lower-cased, a trailing `_arb` dropped, only names starting with `tex1_`), and PNG decoding to 32-bit RGBA with WIC.
- The name follows Dolphin's `TextureInfo` / `HiresTextures` as I remember them, not as read from Dolphin's source (not in the repository): the texture hash covers only level 0 with the size padded to whole blocks, `_m` is set when the texture mode enables mipmaps, and the wildcard is looked up before the full name. Bit-exact compatibility with real Dolphin packs has not been checked; if some pack files are not picked up, compare their names with a dump. Also unverified: C14X2 indices are read as big-endian 16-bit values masked to 14 bits. Not supported: DDS files, Dolphin's special LOD handling for `_arb` mipmaps, and EFB copy replacement (`efb1_`).
- Renderer (`engine/src/gpu/gx_render.cpp`): at start, `games/wiiparty/textures/load/` is indexed (base folder from the new `game::Description::textures_directory`). When a texture read from RAM (never an EFB copy, nor an address that holds a rejected copy) is decoded again because its data changed, its name is computed; a matching file is decoded once, kept in a cache and used instead, at its own size. Sampling uses normalized coordinates with the original size from the registers, so a larger image needs nothing else. If the game uses mipmaps, the `_mipN` files are loaded when their sizes are right, otherwise the mipmaps are generated; the sampler's maximum LOD is lifted for custom textures, as Dolphin does, since a larger image has more levels. The cache entry records whether mipmaps are on, since the `_m` name depends on it. A file that cannot be read is reported once and the original texture is used. `video.dump_textures` writes each texture once (level 0 and its mip levels, RGBA PNG through the F12 PNG writer, which gains an RGBA variant) to `games/wiiparty/textures/dump/`, skipping files that already exist; the name is only computed when a texture is rebuilt, so unchanged textures cost nothing.
- Settings `video.custom_textures` (default 1, `WP_CUSTOM_TEXTURES`) and `video.dump_textures` (default 0, `WP_DUMP_TEXTURES`), also in the launcher's Settings page in English and Spanish. `/games/*/textures/` is ignored by Git.
- Verified: cross build with no new warnings; `runtime_tests.exe` under Wine passes new tests for XXH64 (empty, 1, 3, 39 and 256 bytes, seeds 0 and 0x9E3779B1, expected values from the Python `xxhash` package), the palette ranges, full and wildcard names with and without palette and `_m`, the index (case, `_arb`, extensions, sub-folders, wildcard preference) and a PNG round trip (RGBA writer, then WIC decoding under Wine, alpha kept). The launcher page was checked in an offscreen screenshot. NOT run with the game (it cannot be built in this environment): dumping, loading, the mipmap handling and the sampler change are untested in play.

## GX logic operations and texture offsets of lines and points (2026-09-26)

- The blend mode register (BP `0x41`, PE_CMODE0) was only used for blending. Bit 1 enables a logic operation and bits 12-15 select it (clear, and, and-reverse, copy, and-inverted, no-op, xor, or, nor, equiv, invert, or-reverse, copy-inverted, or-inverted, nand, set); the layout was checked against Dolphin's `BPMemory.h` (`BlendMode`, `LogicOp`) and matches the bits the renderer already decoded (blend enable 0, dither 2, color and alpha update 3-4, factors 5-10, subtract 11).
- The blend state is now derived by one pure function, `wp::gx::blend_state` (`engine/src/gpu/gx_state.cpp`), following Dolphin's `BlendingState::Generate`: with blend enable set, subtract wins over the blend factors; the logic operation applies only when blending is off; the alpha test that can never pass and a target without alpha remove the writes as before; no-op writes nothing except a constant destination alpha. The existing blending results are unchanged.
- Direct3D 11.1 can do logic operations only on an integer (UINT) render target and the EFB here is `R8G8B8A8_UNORM`, so, like Dolphin when the host has no logic operations, they are approximated with blending, and the pixel shader can write 0, 255 or 255 minus the color in place of the TEV result (header bits 2-3). Exact for every value: clear, copy, no-op, set, copy-inverted and invert (the same six Dolphin lists as exact). The others (and, and-reverse, and-inverted, xor, or, nor, equiv, or-reverse, or-inverted, nand) are exact only when each channel of the source and the destination is 0 or 255, for example for masks. Dolphin's own table is not exact even for those values in several entries (and-reverse, and-inverted, nor, equiv, or-reverse, nand), so the table was derived again; or-reverse and nand use the second shader output (the unchanged TEV color) as a blend factor. With a constant destination alpha the alpha channel receives the constant (Dolphin leaves this case unsupported).
- `WP_LOG_GX` prints a line (`GX logic op xor (6), approximated with blending, ...`) the first time each new blend state with a logic operation is created, so a game that uses them shows up in the log.
- Verified: `runtime_tests` checks every operation against the bitwise result by simulating the blend with 8-bit rounding, over all 65,536 source and destination values for the exact ones and over 0 and 255 for the others, for both the color and the alpha factors, plus the priority rules, the constant alpha, the unchanged blending cases and the alpha test. The pixel shader was compiled with Wine's `D3DCompile`. It was NOT run with the game (the game cannot be built here), and no logic operation has been seen in any Wii Party screen.
- Texture offsets of lines and points: SU_LPSIZE (BP `0x22`) holds, besides the line width and point size, a line offset (bits 16-18) and a point offset (bits 19-21) selecting 0, 1/16, 1/8, 1/4, 1/2 or 1 (codes 6 and 7 also give 1); bits 18 and 19 of each texture coordinate's s register (SU_TS0, BP `0x30 + 2n`) enable them for that coordinate. Layout and table checked against Dolphin's `BPMemory.h` (`LPSize`, `TCInfo`), `GeometryShaderManager.cpp` and the software renderer's `Clipper.cpp`; the bits sit above the 16-bit scale that `gx_render.cpp` already reads from the same registers. The offset is in normalized texture coordinates (a full texture is 1), as the renderer's texture coordinates are before the pixel shader scales them by SU_SSIZE.
- `line_point_offsets` (`gx_state.cpp`) decodes them. When a line is expanded to a quad, the two vertices on one side get the line offset added to s; which side follows Dolphin's software renderer: for a line wider than tall, the lower side when it runs to the right and the upper side when it runs to the left; for a taller line, the left side when it runs down and the right side when it runs up. When a point is expanded, the right vertices get the point offset added to s and the lower ones to t, so offset 1 maps a whole texture onto the point.
- Verified: `runtime_tests` checks the decoding (every offset code, the per-coordinate bits, no offset when the code is 0), the choice of side and the addition to the coordinates. NOT run with the game (it cannot be built here), and no line or point with a texture offset has been seen in any Wii Party screen.

## Mii faces: texture cache honours TMEM invalidation (2026-09-28)

- Cause: the Mii face library builds each face texture on the GPU by drawing the face parts (eyes, eyebrows, mouth, mole) into the EFB and copying the result. Each part is decoded into the same small scratch buffer in MEM2 (`90f53xxx`-`90f56xxx`: 36x32 I4, 38x32 and 44x32 RGB5A3 and others), and the game writes BP register `0x66` (invalidate texture memory) before drawing the next part. The texture cache in `engine/src/gpu/gx_render.cpp` trusted any texture already checked in the current frame without hashing it again, so every face made in the same frame reused the parts of the first one: CPU Miis got the same eyebrows (women looked masculine), and HUD icons and in-game faces got the mouth of another Mii (the lips seen in ¡Canastas! and Las puertas del pánico). A diagnostic run on the Free Play Mii lineup found 1168 draws that used a texture whose memory had changed within the frame, and about 150 writes of `0x66` per second.
- Fix: the "already checked" mark is now an epoch that advances at every frame and at every write of BP `0x66`, as TMEM is reloaded from RAM on hardware after an invalidation. `gx.cpp` calls the new `render::invalidate_textures()`.
- Result: the CPU Miis in the lineup show their own faces (for example Julie blonde with red lips, Haru with a female face). The lineup still runs at 60 fps with about 70% guest idle time. The user confirmed ¡Canastas!, Las puertas del pánico, Saltos selváticos, Bote a bote and the guest Miis. Free Play: 75 of 79 entries without faults.
- Also recorded from the user's tests: every game mode was entered and tried (not full games) without faults, and the + and - scrolling sound matches Dolphin.

## Projective texture coordinates divided per pixel (2026-09-28)

- ¡Puños fuera!: the water is drawn with a copy of the underwater scene (`EFB copy` 320x240 RGB565) projected onto a large plane with a projective texture matrix (`XF 0x1042`, STQ). `generate_texture_coordinates` in `engine/src/gpu/gx.cpp` divided s and t by q at each vertex, so the plane, whose vertices lie far behind the camera, got wildly wrong coordinates (values above 100) and showed clamped edge streaks instead of the seabed. The hardware interpolates s, t and q and divides at each pixel.
- Change: `ScreenVertex::uv` holds s, t and q; the input layout passes three floats per coordinate and the pixel shader divides (`projected()`, with the old q = 0 rule kept on the CPU side); line and point offsets are scaled by q; the capture log prints q. `runtime_tests` updated for the three-component coordinate.
- Result: the water shows the corals and seabed like the game's own preview picture; 60 fps.
- Carrera galáctica: its background flashes were not seen in a scripted run saved every 10 frames through the whole race (about 1000 frames checked for sudden colour changes). Probably fixed by this change or the texture cache fix; the user confirmed it plays without flashes.

## EFB copies written to guest RAM (2026-09-28)

- Fotos perrunas: each photo is an EFB copy (320x240 RGB565) to its own buffer. In the results the game changes part of that memory afterwards, so `texture_for` rejected the GPU copy ("hash changed") and read RAM, which never held the photo: a black picture with cyan lines for a moment. On hardware the copy is written to RAM.
- Change: `copy_to_texture` now also renders the copy at 1x into a scratch target, reads it back and encodes it into guest RAM in the texture format the copy produces (I4, I8, IA4, IA8, RGB565, RGB5A3, RGBA8; R8/G8/B8/A8 as I8, RG8/GB8 as IA8), in 4x4, 8x4 or 8x8 blocks with the destination stride from BP `0x4D`. The guest hash is taken after the write, so an unchanged buffer still uses the full-resolution GPU copy, and a buffer the game changes afterwards is decoded from the real data. `gx.cpp` passes the stride.

## Recompilation toolchain verified: jump classification and instruction tests (2026-09-29)

- Unresolved indirect jumps classified (`tools/classify_jumps.py`): every `bctr` that is not a detected jump table was traced back to the register it jumps through. DOL: 167 load a function pointer from memory (virtual calls and callback hooks, usually after a null check), 1 is `Run` in `OSExec` (jumps to a new program's entry) and 1 is the C++ runtime's pointer-to-member call (`lwzx` twice from a vtable). Modules: all 22,127 load a function pointer. None is an undetected `switch`, so emitting them as tail calls through `wp::call` (which fails loudly on an address that is not a function) is correct; the remaining "unresolved" count is a count of indirect tail calls.
- Instruction tests (`tools/instruction_tests.py`, CMake target `translator_tests`, run by `ctest`): an independent reference model written from the PowerPC and Gekko manuals in Python (exact arithmetic with `fractions.Fraction`, single rounding with numpy) generates random cases with a fixed seed; for each case the test program runs the C++ that `recompiler/ppc/emit.py` emits for that instruction and compares every GPR, FPR, paired-single half, CR field, XER bit, LR, CTR, SPRG, GQR and 512 bytes of memory. 4,152 cases over 180 instruction kinds: integer arithmetic with carry and overflow, logic, rotates and shifts, compares, CR logic, `mfcr`/`mtcrf`, `mfspr`/`mtspr`, conditional branches with every BO form and CTR decrement, all loads and stores including update, indexed, byte-reversed, multiple and float forms, `psq_l`/`psq_st` with random GQR types and scales, double and single float arithmetic, `fctiw`/`fctiwz`, `fres`/`frsqrte`, and all paired-single arithmetic, merges, selects, sums and compares. Counted over the DOL and the 115 modules, the game has 14.0 million instructions of 175 kinds; the tested kinds cover all of them except unconditional branches and returns (`b`, `bclr`, `bcctr`, exercised by every run), system and cache instructions handled by the runtime (`rfi`, `mtmsr`, `sc`, `dcbz`, `isync`, `sync`, ...), 5 `mtfsf`, 4 `mffs` and 1,778 words of data inside code sections.
- Faults found and fixed by the tests:
  - `rotate_mask` recursed forever when MB = ME + 1 (a full wrap-around mask); now built bit by bit.
  - `addo`, `subfo`, `mullwo`, `divwo` and the other OE forms did not set XER[OV] and XER[SO]; `Emitter.overflowing` now sets them (none occur in Wii Party).
  - `stfiwx` stored a GPR instead of the FPR's low word (not used by Wii Party).
  - `psq_st` to integer types converted through a 32-bit `long` on Windows before clamping, so values beyond 2^31 saturated to the wrong end; the value is now clamped as a float first, as in Dolphin.
  - MinGW's `std::fma` (without FMA instructions) is not correctly rounded: 1 ulp off in 2 of 24 `fmsub` cases. New `wp::fused_multiply_add` uses the CPU's FMA instruction when present (`__builtin_cpu_supports`) and otherwise a proven software algorithm (Dekker product, 2Sum and round-to-odd, Boldo and Melquiond); `runtime_tests` checks it bit for bit against the hardware on 200,000 random cases.
- Gekko fidelity, ported from Dolphin (see `THIRD_PARTY_NOTICES.md`): `fres`/`ps_res` and `frsqrte`/`ps_rsqrte` now return the hardware's table estimates instead of exact results; single-precision multiplies (`fmuls`, `ps_mul`, `ps_muls0/1`) round the C operand to 25 bits first (`wp::force25`); single multiply-adds (`fmadds` family, `ps_madd` family, `ps_madds0/1`) use `wp::madd_single`, which rounds C to 25 bits and corrects the double-rounding tie as the hardware does.
- The whole game was regenerated and rebuilt (688 s); `ctest` passes 4 of 4 (runtime, translator, lifted and recompiler tests); ¡Puños fuera! plays to the results at 60 fps.
- Progress: recompilation toolchain 95% to 100%.

## Linux, step 2: OpenGL renderer, SDL3 window, input and audio (2026-09-29)

- Renderer: `engine/src/gpu/gx_render_gl.cpp` implements the same `wp::gx::render` interface as the Direct3D 11 renderer on OpenGL 4.1 core (the highest version macOS offers), using the API-independent code in `gx_render_common.cpp`. The TEV, EFB copy, clear, present and overlay shaders are GLSL ports of the HLSL ones, integer for integer (`roundEven` for HLSL `round`, manual integer dot products). Choices that keep the output identical to Direct3D:
  - The vertex shader negates Y so that row 0 of every render target is the top row, as in Direct3D; EFB copies, write-back to guest RAM (`glReadPixels`), scissor rectangles and `gl_FragCoord` then use the same coordinates as the Direct3D code. Only the final present to the window's framebuffer is not flipped.
  - Depth uses `glClipControl(GL_LOWER_LEFT, GL_ZERO_TO_ONE)` when available (OpenGL 4.5 or `ARB_clip_control`), otherwise the shader maps z to `2z - w`; `GL_DEPTH_CLAMP` matches Direct3D's disabled depth clip; the depth compare functions map one to one (`GL_NEVER + mode`).
  - Blending with the TEV output as a factor uses dual-source blending (`layout(location = 0, index = 1)`, `GL_SRC1_COLOR`/`GL_SRC1_ALPHA`), like `SRC1` in Direct3D; early depth testing uses `layout(early_fragment_tests)` when `ARB_shader_image_load_store` is present.
  - Samplers are sampler objects built from `sampler_params`; every texture sets its mipmap level count so that mipmapped filtering never sees an incomplete texture.
  - OpenGL functions are loaded through `SDL_GL_GetProcAddress`, so the game does not link to `libGL`.
- Window: `engine/src/platform/video_sdl.cpp` creates the SDL3 window and the OpenGL context on its own thread, releases the context there and makes it current on the GPU thread the first time the renderer needs it (`video::make_gl_current`). It keeps the Windows behaviour: title with FPS and DSP state, F9 (screenshot binding), F11 full screen, F12 capture, hidden cursor setting, the F10 key routed to the options menu interface (still the no-op menu on Linux), frame saving with `WP_SAVE_FRAME`, and `WP_HEADLESS` (a hidden window so frames can still be rendered and saved). Keys use the existing Windows virtual-key codes of the key map, translated to SDL scancodes, so `input.ini` bindings work unchanged; mouse buttons and wheel map the same way.
- Events: the gamepad thread used to take every SDL event from the queue; now it takes only joystick and gamepad events when the SDL video subsystem is running (the window thread takes the rest), and keeps its old behaviour on Windows, where SDL has no window.
- Audio: the windowed-sinc resampler and queue control of the WASAPI output moved into a `Mixer` class shared by both outputs; on Linux the mixer feeds an `SDL_AudioStream` at 48 kHz (PipeWire or PulseAudio). The log shows the same queue statistics on both systems.
- `engine/CMakeLists.txt` uses these files on Linux when SDL3 is found, otherwise the headless stand-ins.
- Results in WSL Ubuntu 24.04:
  - With Mesa's software renderer (llvmpipe) the game runs at about 10 fps, all of it drawing time. With WSL's GPU driver (`GALLIUM_DRIVER=d3d12`, which maps OpenGL onto the PC's AMD Radeon RX 9070) it runs at 60 fps with 31-36 ms of drawing per second. On a normal Linux PC the system's GPU driver is used directly.
  - Screens compared with Windows: the title screen and main menu (in the window, captured with `xwd`), the Free Play Mii selection with floor reflections (EFB copies), the minigame list, ¡Puños fuera! with the distorted water and corals (indirect texturing) and Cinturón de asteroides playing to 21 seconds, all matching the Direct3D output. Keyboard (A+B on the title screen with Enter and Backspace) and mouse (pointer and clicks through the menus) work in the window. Audio plays through PulseAudio with no missing frames.
  - Windows: the game still builds without warnings, `ctest` passes 4 of 4, and ¡Puños fuera! runs at 60 fps with WASAPI output and no missing audio frames.
- Open issue: once, while starting Cinturón de asteroides by hand in the Linux window, the game stopped with "call to unknown function 8013fbd0". That address is the return point of the context save inside `OSSelectThread`: a guest thread was resumed whose saved host context (`g_saved` in `threads.cpp`) was no longer recorded, so the engine tried to start it as a new thread at that address. Six later scripted runs through the same minigame (with and without a window, with input logging, with the sideways grip flag) did not repeat it, so it depends on timing. The next step is to record the context save, load and discard history and print it when a thread is resumed at a mid-function address.

## Linux, step 3: F10 options menu and custom textures (2026-09-29)

## Launcher offline mode (2026-09-29)

- New "Offline mode" setting (`offline=1` in the launcher preferences): the launcher never connects to the internet. The update check is skipped (its switch shows off; turning it back on leaves offline mode), and the install never downloads tools: a missing tool stops the install with a message that names it and offers three ways out (the offline tools pack, installing it yourself, or turning offline mode off). Without offline mode the behaviour is unchanged.
- Offline tools pack support: the toolchain also looks in a `tools` folder next to the launcher, with the same layout as the downloaded tools (`tools/nodtool`, `tools/python`, `tools/cmake/...`, `tools/ninja`, `tools/mingw/...`), and puts it first on the PATH. Tools found there are listed in the install log as "(offline pack)" and are never downloaded.
- Checked on Linux: the switch writes the preference, turns the update check off and the install log path builds on both systems.
